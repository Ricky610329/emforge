1　摘要：這是什麼、解決什麼問題

1.1　一句話

emforge 是一個昂貴模擬下的設計搜尋平台：把有限的模擬機時當成稀缺資源來調度， 用累積下來的量測資料庫決定「下一批要燒什麼」。 它不是一個演算法，是一個讓各種演算法能被公平地跑、比較、記帳的執行環境。

依據：pyproject.toml 的 description、README.md、docs/architecture.md §1。

1.2　問題形狀

docs/architecture.md §1 把適用範圍寫成四條同時成立的條件：

  1. 評估一個候選要跑昂貴的模擬——本專案是 HFSS，一筆 100–200 秒。
  2. 參數空間大且離散——25×25 二值遮罩＝2625 種。
  3. 規格由領域專家定，而且會改——本專案改過三次。
  4. 目標不是「最佳解」，是「在有限機時內找到夠好且可製造的解」。

反過來說，同一份文件也明講不適用的場景：模擬便宜（直接跑演化演算法就好）、參數連續可微（用梯度）、規格永遠不變。 把這條寫進架構文件，是為了讓接手的人不要把它當成通用最佳化框架來用。

1.3　兩個硬性約束（同時是驗收條件）

約束意思在程式裡怎麼落實
沒有 AI 也能用 AI 是加值層，拔掉它，系統要能自己跑一整晚。 runtime 的排程迴圈（emforge/runtime/）沒有任何 LLM 呼叫；狀態全在磁碟、可中斷續跑。
平台不綁定策略 研究出來的方法只是「幫使用者做得更好」，使用者不一定要用。 策略＝一個 .py 檔，只要有 COMPATIBLE 與 propose(ctx)（emforge/strategy.py）；內建只出貨兩個最小策略。

依據：docs/architecture.md §1「兩個硬性約束（來自委託人，也是驗收條件）」。

1.4　與舊系統 Antenna 的關係

emforge 是另一個 repo、另一套契約，不是 Antenna 的重構分支。舊系統 Antenna 把生成器、代理模型、 線上學習、批次 HFSS 驗證線、判讀腳本綁在一起；emforge 只保留其中「平台」的那一半——排程、去重、派工、量測、 評分、公證、記帳——並把天線領域關進兩個受控接點：

  • adapter：emforge/adapters/antenna/ 是唯一會 import torch／antenna 的地方， 透過環境變數 EMFORGE_ANTENNA_REPO 把舊 repo 掛進 sys.path（adapters/antenna/_bind.py）。
  • 匯入器：emforge/legacy/antenna_import.py 把舊 NAS 樹的歷史量測讀進新資料庫，只讀舊樹。

核心「零領域依賴」不是慣例而是被測試釘死的：tests/test_smoke.py::test_core_modules_never_import_torch_or_antenna 用 AST 靜態掃描整個套件，adapters/ 與 legacy/ 以外的模組出現 torch/antenna/win32com/scipy/matplotlib/pandas/loguru 就紅。

1.5　兩個目標

目標一：算法與基礎設施都解耦

第一層解耦是「算法不進平台」——策略只提案，去重／派工／評分／公證是 runtime 服務。 第二層解耦是 M12（2026-09-06）做的：把所有共享協調狀態抽到 Depot 介面後面 （emforge/depot/）。原本散在各處的 open()／os.replace／O_EXCL 全部收成十幾個原語； 今天的 FileDepot 逐位元重現原本的 NAS 佈局，未來換 S3 或 SQL 只要實作同一組原語並通過契約測試， runtime／worker／db 的邏輯一行都不用改。

動機記在 docs/implementation.md §13：「Ricky 2026-09-05：不倚賴特定渠道、支援多種部署（日月光）；『算法、基礎設施都解耦』」。

目標二：儀器層讓 AI agent 安全地直接量

M13–M16（同樣是 2026-09-06）在 worker 與模擬器之間插入一層 Instrument（儀器）：狀態機、租約、 硬限制、前置檢查、兩段式確認、三層急停、自動產生的說明檔。接著每一台正式機各自是一個 MCP server， 把儀器的程序一對一貼成 tools。這讓 AI 層除了「讀狀態、寫策略檔」之外，多了一條對單台機器下單跑一筆的路徑—— 但每一步都有人在迴路的閘（confirm token、allowed_profiles、急停解除只能走 CLI）。

依據：docs/architecture.md 末節「與實作的偏差（M13–M14／M15–M16）」、emforge/device/。

2　設計原則：D1–D10 與三條貫穿性規則

docs/architecture.md §11 把十條設計決定編號成 D1–D10。它們不是風格偏好， 每一條都指向舊系統的一次具體失敗或委託人的一句具體要求。以下逐條說明「原則、理由、在程式碼的落點」。

2.1　D1　評估可掛載；runtime 統一算分，策略診斷只當附註

原則：量測分成兩層——measure（原始響應 → 軸值，凍結）與 spec（軸值 → 一個分數，可換）。 分數只在 runtime 算，策略不准自評。

理由：委託人明說「有 AI 加值的好處是我可以很善變我的評估系統」。舊專案的規格被專家改過一次 （帶內門檻放寬 2 dB、阻帶放寬 5 dB），不必重量任何資料就把缺口從 6.1 降到 3.05 dB—— 做到這件事的正是「量測凍結、評分可換」。另一面，策略自評等於「離線考」，舊專案三度證明離線考 ≠ 實戰考。

落點：emforge/specs.py（register_measure 綁定 targets 後凍結、register_spec、 measure()／score()）；emforge/model.py::Spec.score＝min(measure[axis] + offset)，缺軸或 NaN 回 None； 評分只在 emforge/runtime/collect.py 發生；換評估器走 emforge/ledger.py::rescore（零重量）。

2.2　D2　一個 runtime 實例綁一個 sim_profile

原則：一個行程只服務一種模擬；要跑第二種＝開第二個實例。

理由：委託人要求「不要允許 single 跟 dual 同時跑，不然有點混亂」。實例綁定之後， 沒有 per-batch 的 config 可以漏（這正是事故 I-6 的成因），資料庫視圖自動是該 profile 的世代， 策略的 COMPATIBLE 只要在載入時檢查一次。

落點：Runtime(root, profile_name)；單例鎖的 key 是 runtime_state/<profile>/lock； Database(depot, write_profile=…) 拒寫別的 profile（ProfileWriteRefused）； strategies.yaml 的 profile: 與 --profile 不符直接 ConfigError。

2.3　D3　每個評估器版本一榜，舊榜凍結不刪

原則：榜（ledger）的身分是 (profile, spec) 對；換 spec 就建新榜，舊榜一個 byte 都不動。

理由：舊專案現行做法（三代榜並存）已驗證可行。

落點：paths.ledger_file(profile, spec) → ledger/<profile>/<spec>.json； ledger.rescore 掃 db 每筆重算 score 建新榜，榜已存在需 --force（exit 6）。

2.4　D4　策略＝一個 .py 的 propose(ctx)；狀態靠 workdir，回饋靠下一 tick 讀 db；沒有 callback

原則：策略只有一個進入點。要有狀態就寫進自己的 workdir（runtime 永不讀它）； 要看上批結果就下一 tick 從 ctx.db 讀。

理由：委託人定調；舊專案的 grind_loop 證明「每 tick 呼叫 ＋ 狀態在檔案」足以承載需要重訓的策略。 沒有 callback 意味著策略永遠不會被要求「在某個時刻同步回應」——這讓子行程隔離變成可能。

落點：emforge/strategy.py（load_strategy／check_compatible／make_context／ propose_in_subprocess）；Context 的 workdir 由 paths.strategy_workdir(root, profile, strategy) 給。

2.5　D5　機時＝靜態 prio；背景填空只在佇列空時跑

原則：策略在 strategies.yaml 宣告一個靜態 prio（小者先）； prio >= background_prio 的是背景填空，只有在「沒有前景 inflight 且 佇列沒有排隊 job」時才排。

理由：委託人「會有背景填空閒的 agent」。

落點：emforge/runtime/schedule.py::_background_allowed。注意它看的是全機共用佇列， 所以另一個 profile 的實例有 job 排隊時，這個實例的背景策略也不派——設計如此，但容易被誤讀成「卡住」 （記在 docs/implementation.md §12-6）。

2.6　D6　era ≡ sim_profile 名，不另設欄位

原則：「世代」不是一個獨立欄位，就是 profile 的名字。改 profile 內容＝換新名字（append-only）。

理由：事故 I-7——舊幾何底板讓零厚度對角接觸成為數值幻影，換代之後舊資料不是變錯，是變不可比。 如果「世代」與「profile 名」是兩個必須永遠一致的欄位，那就是 I-6 型事故的溫床。

落點：record_id = sha1(packbits(bits) + sim_profile)[:16]——同樣的 bits 在不同 profile 下是不同設計 （emforge/model.py::record_id）；資料庫實體分目錄 db/<profile>/； profiles.register_profile 同名不同內容拋 RegistryConflict；report 預設拒絕跨 profile 並排（exit 2）。

2.7　D7　去重、派工、評分、公證是 runtime 服務；策略只 propose

原則：安全閘不可被繞。kind=repeat（公證重測）只有 runtime 的公證流程與 cli smoke 能設。

理由：事故 I-8——查重閘接在管線裡，退出碼被尾端指令吃掉，安全閘靜默失效。 與「迴圈不自己加冕」：自動化流程可以觸發公證，但不能宣告紀錄成立。

落點：Proposal.from_dict 用嚴格鍵集——多出 kind／sim_profile／score 一律 ProposalError； runtime/dispatch.py::dispatch 的簽名沒有 skip／bypass／keep_* 參數（測試釘死： tests/runtime/test_dispatch.py::no_dedup_bypass）；策略拿到的是 db.View， 結構上就沒有寫入方法（不是被禁，是不存在）。

2.8　D8　對照臂不強制；arm="blind" 是保留語義

原則：不強迫每個策略都跑對照組，但 blind 這個 arm 名保留給「零演算法對照臂」； blind 樣本數不足 k_min 時，報表只印數字、不印任何比較。

理由：「策略 X 比較好」只在同批有零演算法臂時說得出口。

落點：emforge/report.py（blind_count、p_beats_blind、_render 的 show_p 閘）； 內建策略 emforge/strategies/blind.py 每筆都標 arm="blind"。

已知限制：arm="blind" 是策略自我宣告，契約無法驗證——說謊會留紀錄但不會被擋 （docs/implementation.md §12-5）。

2.9　D9　策略連續 3 次例外 → runtime 暫停它（操作保護，不是淘汰）

原則：策略出錯不會殺 runtime，但連續失敗會被暫停，等人或 AI 用 emforge resume 重啟。

理由：事故 I-4——背景自產路徑拋出例外，直接殺掉兩台機器的 worker 行程。 歸納成一條鐵則：背景／填充等級的工作絕不能有能力終止執行器。

落點：runtime/schedule.py::_propose 把所有例外接住 → strategy_error 事件、errors_consecutive += 1； 達 strategy_error_limit（預設 3）→ paused＋strategy_paused 事件。 更外一層：策略正式跑在子行程（propose_in_subprocess），逾時可殺、記憶體尖峰不傳染。

2.10　D10　keep_project 不在 Profile／Proposal 任何欄位

原則：「保留模擬專案檔」是交付動作，不是儀器屬性，所以它不出現在任何契約欄位裡。

理由：事故 I-1——78 個工作的模擬暫存目錄吃光系統碟，導致求解器連環 COM 例外，重開機是假好轉。 把 keep_project 放進 profile 等於讓策略能開它，會重演磁碟塞爆。

落點：契約裡沒有這個欄位（測試 tests/test_model.py::…no_keep_project_field）； 工作目錄的清理有兩道——run_batch 結束（done／fail／yield 皆）刪，worker 啟動時整清 （emforge/worker/workdir.py、emforge/fs.py::sweep_dirs）。

2.11　三條貫穿性規則

（a）迴圈裡沒有 LLM

這是整個系統最強的一條。emforge/runtime/ 六個檔（core／reconcile／dispatch／ collect／schedule／notarize）裡沒有任何模型呼叫，也沒有任何需要「外部有人在」的假設。 AI 層與系統的介面是「改檔案、跑命令列」——所以任何 harness 都能扮演，人也能扮演。 喚醒源是 watch 的 exit code、events.jsonl 追檔、或 status.json，不綁定任何特定 agent 框架。

依據：docs/architecture.md §10、docs/implementation.md §10。

（b）append-only 註冊表

三個註冊表都是 append-only，同名不同內容一律拋 RegistryConflict，而不是覆蓋：

註冊表身分（怎麼判「同不同」）位置
measure（量測尺）函式的 module+qualname ＋ labels ＋ targets 的 canonical JSONspecs.py::Measure.key
spec（評估器）整個 frozen dataclass 相等specs.py::register_spec
profile（儀器）profile_hash ＋ shape ＋ labels ＋ n_points ＋ spec ＋ timeout_s ＋ retired ＋ fixed_onprofiles.py::_same

重跑同一份 registry.py 是 no-op；內容改了就撞衝突——這正是要的行為，因為「改內容 ＝ 換名字」。

（c）config 驅動

兩份使用者可寫的設定構成整個實驗介面，兩份都不是 Python 以外的 DSL：

  • <root>/registry.py——模擬庫與評估器的註冊表。runtime 與 worker 啟動時都執行它 （profiles.load_user_registry 用 runpy），所以派工端與執行端看到同一套 profile／spec。
  • runtime_state/<profile>/strategies.yaml——這個實例跑哪些策略、各自的 prio／batch／ max_inflight／params，以及 runtime 的十個數值旋鈕。改了之後 runtime 每 tick 比內容 sha1 （不看 mtime）決定要不要重讀；解析失敗發 config_invalid 事件、沿用上次有效設定，不停 runtime。
strategies.yaml 的所有數值都是佔位預設。noise_floor／k_min／quiet_s／ max_error_rate／strategy_error_limit 沒有任何一個經過本問題域以外的校準 （emforge/strategy.py::RuntimeConfig 的 docstring 與 docs/implementation.md §12-2 都明講）。 跨域使用要全部重調。

架構文件對「四個欄位為什麼缺一不可」的說明值得複述，因為它們是這個資料模型的全部理由： 幾何宣告（bits ＋ profile）——可製造性處理（橋、槽、像素尺寸）是幾何的一部分，不是事後濾鏡， 同 bits × 不同橋寬 ＝ 不同量測對象；量測條件（profile_hash）——結果自帶「這批用什麼設定量的」，不靠人記； 原始響應——導出指標會隨評估器改版，原始曲線不會；世代（≡ profile）——沒有它， 三年後接手的人會拿跨代數字做決策。

6　Depot 抽象：基礎設施解耦

6.1　為什麼要有這一層

2026-09-01 的第一版把「共享狀態」直接寫成 NAS 上的檔案：O_EXCL 建檔認領、os.replace 原子替換、 mtime 當心跳。這在自家實驗室成立（舊系統以此在 NAS 上跑了兩個月），但部署形態未定—— 合作企業的環境不一定有共用 SMB 檔案系統。M12（2026-09-06）把這一層抽成 Depot 介面。

動機出處：docs/implementation.md §13「Ricky 2026-09-05：不倚賴特定渠道、支援多種部署（日月光）；『算法、基礎設施都解耦』」。

抽象的設計目標是最小共同集合：只用 S3（If-None-Match: * 的條件 PUT、版本化 DELETE）、 SQL（唯一鍵 insert、DELETE … WHERE updated_at < …）與檔案系統（O_EXCL、os.replace） 三者都做得到的原語。所以介面裡沒有 rename、沒有 compare-and-set， 列舉語義刻意寫成「可最終一致」。

6.5　契約測試：換後端為什麼能零改 runtime

tests/depot/test_contract.py 是「基礎設施解耦」的機器版：36 條測試，用 pytest 參數化對每個後端各跑一次 （@pytest.fixture(params=["file","memory"])），加上兩個後端各自的專屬測試，depot 目錄共 89 條。

契約涵蓋的性質，挑幾條有代表性的：

  • 原子替換在並發讀者下成立——讀者永遠拿到完整的舊版或新版。
  • 序列化失敗時不動舊 doc（put_json 先序列化再寫）。
  • 8 條執行緒同時 claim，只有一個贏。
  • release(owner=別人) 拒絕且保留租約；touch 對不存在的 key 是 no-op 且不建檔。
  • key 可以含中文與撇號——因為真實 NAS 路徑是 T:\碩二_鄒穎麒's\antenna\…， 測試的 root fixture 也刻意做成 tmp_path/"碩二_x's"/"emforge"。
  • 大 npz bytes round-trip、lock 序列化 8 條執行緒的計數器、 lock 逾時拋 LockTimeout 而不是 SystemExit。

只要一個新後端通過這 36 條，runtime/、worker/、db.py、queue.py 的邏輯就一行都不用改—— 因為它們只認得這些原語，而這件事由 test_smoke.py 的三張清單靜態保證（見 4.3）。

6.6　關鍵發現：Windows 上兩個並發 rename 可以都成功

發現：M12a 的契約測試實際抓到——Windows 上兩個執行緒同時對同一個檔做「rename 到不同目標」， 可以兩個都回報成功（第二個經由先開好的 handle，把已經改過名的同一個檔再改一次）。

這推翻了第一版的一個假設：「破鎖＝rename，恰好一個人成功，所以破鎖本身就是仲裁」。 系統據此做了一個明確的裁決，寫在 depot/file.py 的 #! 事故疤註解裡：

破鎖不是仲裁，claim（O_EXCL）才是。破鎖只保證「搬到的不是別人的新鎖」； 破完一律接 claim，誰 claim 到誰算。

三個地方因此改寫：

  1. Depot.break_if_stale 的介面契約直接寫明「並發破鎖者可能不只一人 True」 （depot/base.py），而不是承諾唯一性。
  2. FileDepot.break_if_stale 加了 mtime 身分檢查：搬完之後比對被搬走那個檔的 mtime， 若不等於當初判定過期的那一個，表示搬到的是別人剛建的新鎖 → 用 _undo_break 放回去 （Windows 用 os.rename、POSIX 用 link+unlink，目標已存在就不覆蓋），這次算沒破到。 破鎖留下的 <name>.broken.<pid>.<rand> 證據檔不刪（給 doctor 數），且不會被 list 列出來。
  3. 所有呼叫端都改成「破完必 claim，claim 的回值才是勝負」： Queue._claim（queue.py）、Runtime.acquire_lock（runtime/core.py）、 Depot.lock（depot/base.py）。.fail 檔的接管則用 delete() 的回值仲裁 （「True ＝這次呼叫移除了它」）。

這個性質被契約測試釘住：test_two_breakers_never_delete_each_others_reclaim_and_claim_arbitrates—— 兩條執行緒同時破一個過期租約，斷言「破成功的可能有 1～2 人，但 claim 到的恰好一人， 而且輸家事後既破不掉、也 release 不掉贏家的新租約」。同一條測試對 MemoryDepot 也跑， 因為未來的 S3 版本化 DELETE 也是冪等的——同樣可能多人成功。

別的 profile 的 job、cli:* origin 的 job 都不歸這個 runtime 管，不列入對帳。 這條防線來自事故 I-14：「在未落地的狀態上又疊了三層工作」。

fleet_quiet：排隊 ≠ 停滯

「有派出去的批，但 quiet_s 內整個機隊沒有任何產出」時，runtime 只等、不排程—— 避免在機器已經塞住時繼續往佇列堆東西。「產出」的定義有三個來源，取最新的： inflight 檔本身的 modified_at、該批最新結果檔的 modified_at、 以及（M14 加的）正拿著我們某批在跑的儀器，其狀態字典的心跳—— 因為一筆 HFSS 可能長過 quiet_s，只看結果檔會誤判成停滯。

8.3　collect：收結果的終態語義

runtime/collect.py 是 2026-09-05 獨立審查改動最多的一個檔， 它的四條 #! 事故疤註解各對應一個真實的資料遺失風險：

規則內容與理由
profile_hash 比對 結果檔自帶量它的儀器指紋；與註冊表不符 → 發 profile_tamper 事件、不入庫 （但記為已收，不重複讀）。代表有人改了 registry.py，或某台在跑舊程式。（I-10）
error 等批 done 才收 error 結果在批未 done 前不入庫、不記 collected——因為 worker 的補測輪會覆寫同一個結果檔（翻案成 done）。 先記了就永遠不會再讀，翻案的 HFSS 結果白燒。批到 done 終態才把殘留 error 收進 db。（review-1）
fail 不是終態 .fail 只代表「這台判死」，名單外的機器會接管重跑。所以只發一次 batch_failed （inflight 記 fail_reported）、inflight 留著繼續收。真的沒人接，由人下 emforge abandon。（review-2）
每筆立刻落地 每入庫一筆就立刻把 collected 寫回 inflight 檔。若上次死在「add 成功、 collected 沒落地」之間，這次 add 會回 False——但仍然算新收、交給 notarize， 不能靜默漏掉一個破榜設計。（review-8）

冪等性因此有三層：Database.add 同 id 同 store 已存在直接回 False（不覆寫，I-15）； collected 讓 Batch.results(known_ids=…) 只開新檔（I-5 增量）； _persist_inflight 在寫回之前先確認 inflight 檔還在（被 abandon 拿掉的不復活）。

批 done 且 set(inflight.ids) ⊆ collected 才算真的收完：移除 inflight、發 batch_done。 此時若 kind=sample 且錯誤率 > max_error_rate，就暫停整個 profile （paused_profile＋profile_paused 事件）——注意暫停的是 profile，不是策略： 高錯誤率是儀器或機器的問題，不是策略的錯。

8.4　dispatch：派工是一個動作

8.6　notarize：迴圈不自己加冕

這是整個 runtime 唯一會設 kind=repeat 的地方，也是唯一與「紀錄」有關的自動化—— 但它永遠不寫榜。

開新候選

門檻 = max( 榜首 score（經 Ledger.best() 走 checksum；被手改 → ledger_tamper 事件、當作沒有榜）,
            pending 裡最好的 conservative,
            目前正在公證中的候選 score )

for rec in 本 tick 新收、status=done、score 非 None、kind=sample 的紀錄（依分數降冪）:
    已在公證中或已在 pending → skip
    score ≤ 門檻            → skip
    派 repeat_n 個重測批（store 名 <profile>-notarize-t<tick>-<id8>-r<n>，prio=notarize_prio）
        派不出去 → dispatch_failed 事件、**不登記候選**（review-3）
    登記 nz[id] = {stores, tick, score}；事件 record_candidate + notarize_dispatched
    門檻更新為該分數

判定

重測批全部離開 inflight（佇列狀態是 fail 的不算、不擋，否則會等到天荒地老）之後： scores = [原始分數] + [每個重測批的分數]； spread = max - min，conservative = min。

  • spread ≤ noise_floor → append 一筆到 pending.jsonl （{id, tick, scores, conservative, spread, stores, at, status:"待審（迴圈不加冕）"}）＋事件 notarize_pass。
  • 否則 → 事件 notarize_reject（分數不穩＝可能是假象）。
  • 只剩一個分數（重測全掛）→ 也算 reject，不猜。
設計上的分界線：runtime 可以說「這個候選我重測過，三次一致，保守值是 −2.31」； 它不能說「這是新紀錄」。後者是人或 AI 的 promote——而且 promote 會把「誰換的王」 記進 by 欄與 history。

8.7　ledger：榜怎麼被保護

機制內容
唯一寫路徑只有 Ledger.promote 與 ledger.rescore 會寫 ledger/<profile>/<spec>.json； CLI 是 emforge promote／emforge rescore。runtime 沒有任何寫榜的路徑。
_checksum寫入時算全文（不含 _checksum 自己）的 sha1[:16]；每次 read() 都驗， 不符拋 LedgerTamper。這是「繞過會留下紀錄」而非「不可能」。
必須在 pendingpromote 要求 id 在 pending.jsonl；--force 可以繞， 但榜上會記 force: true。
必須帶 --by沒有 by 直接 ValueError——「誰換的王」是必填。
分數用本榜的 spec 重算promote --spec other_v3 時不抄 pending 裡（用 profile 預設 spec 算的）分數， 而是用該榜的 spec 對 db 裡所有量測重算後取 min。（2026-09-05 審查砍掉的四條之一）
history append-only每次 promote／rescore 都 append 一筆，記 prev_id／prev_score／by／note／force。
rescore 拒絕換尺spec.measure != profile.measure 直接 ValueError： 「換尺＝換儀器，不是 rescore」。

已知漏洞（docs/implementation.md §12-17）：promote --spec 的重算用 Record.measure（量測凍結）； 若那個 spec 換了 measure 名，rescore 會拒，但 promote 不會——它只檢查 spec 名有沒有註冊。

9.2　驗證規則（strategy.validate_proposals）

任一筆不合規，整批拒（策略要自己修，平台不替它猜）：

  1. 回傳值必須是 list／tuple。
  2. 筆數 ≤ ctx.budget。
  3. 每筆只能有 pattern／parent／arm／note 四個鍵（多一個就 forbidden_key）。
  4. pattern.shape == profile.shape。
  5. pattern 是 bool，或值只含 0／1（會被轉成 bool）。
  6. pattern[profile.fixed_on] 必須全為 True——饋墊像素不可翻。

9.3　子行程隔離

runtime 正式呼叫策略一律走 propose_in_subprocess： 

python -X utf8 -m emforge.strategy --root R --profile P --strategy S \
       --budget N --seed S --tick T --params '{…}' --out <workdir>/_proposals.npz [--depot spec]
  • 逾時可殺：subprocess.run(timeout=…) → StrategyTimeout。
  • 例外不傳染：非零 exit code → StrategyFailure，訊息帶 stderr 最後 8 行。父行程永遠活著（I-4）。
  • 記憶體尖峰不傳染：策略載大模型、掃全史都在子行程裡（I-5）。
  • 交接檔無 pickle：_proposals.npz 存 patterns／parents／arms／notes （notes 是 JSON 字串陣列）。空提案也要落檔，父行程才分得出「回空」與「沒跑完」。
  • 子行程用 --depot <spec> 重開後端。memory:// 子行程看不到——所以 emforge run --depot memory://… 自動改成 in-process。

代價：每 tick 每策略多 1–2 秒的子行程啟動時間；策略多時 tick 會變慢。這是刻意用效能換 I-4 隔離的取捨 （docs/implementation.md §12-10）。

9.4　載入順序與 workdir

resolve_strategy_path(root, name)：使用者的 <root>/strategies/<name>.py 優先， 其次內建 emforge/strategies/<name>.py。保留字與不合規的名字在解析階段就拒。

workdir ＝ <root>/runtime_state/<profile>/strategies/<name>/，由 make_context 自動建立。 它是本機路徑、runtime 永不讀它——這兩點加起來就是「有狀態策略」的完整支援： 模型權重、快取、上次的分布統計都放這裡，平台完全不管內容，換 depot 後端也不必跟著搬。

COMPATIBLE = {"*"}

def propose(ctx):
    k, d = int(ctx.params.get("k", 10)), int(ctx.params.get("d", 3))
    free = np.flatnonzero(~ctx.profile.fixed_on.reshape(-1))   # 饋墊不可翻：事實來源是儀器
    top = ctx.db.top(k)
    if not top:
        return []                       # 資料庫空 → 交給 blind 打底，不硬湊
    per = -(-ctx.budget // len(top))    # ceil：把 budget 填滿
    out = []
    for rec in top:
        for _ in range(per):
            q = rec.bits.copy().reshape(-1)
            q[ctx.rng.choice(free, d, replace=False)] ^= True
            out.append(dict(pattern=q.reshape(ctx.profile.shape), parent=rec.id, note={"d": d}))
    return out[:ctx.budget]

去重、饋墊檢查、seed 記錄、派工、掛偵測、評分、公證——沒有一樣在這 25 行裡。 註冊只要在 strategies.yaml 加一行 - {name: top_k_flip, prio: 3, batch: 60, params: {k: 10, d: 3}}。

檔職責
loop.py主迴圈：STOP → 急停 → Queue.pick → gate → 儀器租約 → run_batch → mark_done／mark_fail。 啟動時載入本機 registry.py、印 worker_ver（I-10）、清工作目錄（I-1）、寫 worker_start。

run_batch 的流程

建工作目錄 → bind(profile, wd, store) → open_with_retries（3 試，各 300 s 看門狗）
第 0 輪   跑「還沒 done **且 attempts < 3**」的（＝續跑；毒樣本三振後不再跑，review-10）
補測輪×2  跑「error 且 attempts < 3」的（每輪之前殺透重開）
  每一筆：
    急停？                → job_yield(estop_engaged)，放掉**自己的** claim（別台可續跑）
    guarded_call(simulate, timeout_s, kill, abort_if=急停, poll_s=5)
    寫 batches/<store>/results/<id>.json（含 machine／worker_ver／profile_hash／attempts）
    queue.touch_claim(store)                     # claim 心跳
    error?  aborted:…      → yield（吃一次 attempts、**不重開**、不算保險絲）
            watchdog_…     → 殺透重開
            第 0 輪        → 保險絲（cooldown／blown）
            補測輪連 3 敗   → 放棄本輪
    每筆之後：claim 被別台接走 → "yield"（**不動別人的 claim**）
              背景 job 遇前景 queued → 釋放 claim、"yield"
finally: close ＋ 刪工作目錄（done／fail／yield 皆刪）
回傳 "done" | "yield" | "fail"

11.5　急停：三層，解除只能 CLI

層key／路徑誰能按特性

檢查順序 fleet → device → local，回報最外層那一個。急停生效後有四個效果：

  1. Instrument.open()／simulate() 硬擋（拋 EstopEngaged）。
  2. 正在跑的那一筆由 guarded_call(abort_if=…, poll_s=5) 殺掉 → 結果 error: aborted: estop_engaged （吃一次 attempts、不重開、不算保險絲）。
  3. worker 每筆之前讓位（放掉自己的 claim，因為急停可能只停這台，別台可以續跑）。
  4. worker 主迴圈在 job 之間不撿新工作（等 poll_s 再看）。

解除只有一條路：emforge device-estop clear [--tag T | --local] --confirm。 MCP 沒有 device_estop_clear 這個 tool——這件事被 docs/naming.md 明列， 也被 device/reference.py::PROCEDURES（tools 名單的唯一真相）與其對帳測試釘住。

誠實的限制（docs/implementation.md §12-21）：三層都是「檔存在即真」，沒有簽章—— 任何能寫 depot 的人都能 engage／clear；clear 走 CLI 只是流程約束，不是權限。 另外，急停到真的殺掉正在跑的那筆最多晚 5 秒（estop_poll_s）； 三次急停剛好落在同一筆上，會把它三振成毒樣本。

11.7　兩段式確認

token = sha1(f"{secret}|{op}|{key}|{window}")[:8]        # window = int(now // 600)，10 分鐘一格
第一次呼叫（不帶 confirm） → {"needs_confirm": True, "token": …, "record_id": …, "preview": {…}}
第二次呼叫（帶 confirm）   → check_confirm（本窗或上一窗，且沒用過）→ 真的跑 → consume_confirm

secret ＝ EMFORGE_DEVICE_TOKEN（沒設就用隨機值，等於只有本行程能算）。 token 綁定操作與對象（op／key），所以「確認要跑 A」不能拿去跑 B。

驗證與消費是分開的：check_confirm 只驗、consume_confirm 在操作真的開始之後才呼叫。 理由寫在 Instrument.check_confirm 的 docstring——被拒（儀器忙／急停）就燒掉 token 的話， 使用者十分鐘內不能重試（同窗內 token 同值）。這是 M15 的測試抓到的。

  • 非 loopback 綁定 ＋ 沒有 token → 拒起（check_bind，CLI exit 1）。 loopback 則沿用 SDK 的 DNS-rebinding 防護（Host 白名單）。
  • 為什麼不用 SDK 的 token_verifier／AuthSettings：那條是 OAuth 資源伺服器模型 （要 issuer_url／resource_server_url、掛 /.well-known 端點），而共享密鑰不是 OAuth。 中介層 15 行、而且可以用 httpx2.ASGITransport 免 socket 測試。（docs/implementation.md §13）
  • 傳輸模式：stateless ＋ JSON response（streamable_http_app(json_response=True, stateless_http=True)）—— 每個請求獨立、沒有 session、沒有 SSE 推送。

12.5　與 worker 同行程

emforge worker --root R --serve [--host H --port N]
  → check_bind(host, token)                     # 先拒再起儀器
  → inst = make_instrument(root, tag, …)
  → inst.start()
  → serve_in_thread(inst, host, port, secret)   # uvicorn 在 **daemon thread**
  → worker_loop(root, tag, instrument=inst, …)  # 主執行緒跑 worker 迴圈，共用同一台儀器

emforge device-serve <tag> --root R           # 只服務、**不撿佇列**（單筆試量，或這台暫時不當 worker）

同機只能有一個 HFSS 使用者，所以 MCP 與 worker 必須共用同一個 Instrument—— 租約在行程內仲裁。uvicorn 跑在 daemon thread 意味著 worker 主迴圈結束、行程結束，MCP 也跟著沒了—— 設計如此；要「沒有 worker 的 MCP」就用 device-serve。

14.3　單寫者原則與它的一個例外

三條日誌各自只有一個寫者：runtime 寫自己的 events.jsonl／pending.jsonl； 每台 worker 寫自己的 queue/log/<tag>.jsonl；每台儀器寫自己的 devices/<tag>/log.jsonl。 理由在 fs.py 的檔頭：SMB 上多寫者 O_APPEND 交錯無保證， 所以「多方各跑一次」的匯總一律「一方一檔」（I-15 的歸納）。

已知的低頻例外（docs/implementation.md §12-7）：CLI 的 promoted／retired／rescored／batch_requeued／batch_abandoned 會 append 到 runtime 的 events.jsonl，違反單寫者契約。頻率極低（人的操作）， 但在 SMB 上理論上可能與 runtime 的寫入交錯。

15　品質保證

15.1　TDD 與紀律

CLAUDE.md 的四條硬規則裡有兩條直接關於測試：

  • 先寫紅測試 → 實作 → 綠。回歸測試的 docstring 首行固定寫 回歸 I-N（日期）：防止…，I-N 指向 docs/incidents.md。
  • 一里程碑一 commit：python -m pytest 全綠 ＋ python -m pyflakes emforge tests 無 undefined name 才 commit。

三條測試紀律值得單獨指出，因為它們都是舊系統的教訓：

紀律內容
測試永不碰 NAS tests/conftest.py 有一個 session 級 autouse fixture 把 EMFORGE_ROOT 從環境拿掉， 強迫所有測試走 root fixture。而 root fixture 的路徑刻意是 tmp_path/"碩二_x's"/emforge——含中文與撇號，因為真實 NAS 路徑就長這樣， 靠字串拼接的路徑處理在這裡就會炸。
沒有 golden、沒有自動寫回基準 來自事故 I-9：本機用 CI 模式（較寬容差）跑測試，比對「通過」後框架把當前值靜默寫回基準檔。 emforge 完全不用這個機制。決定性只在同 seed 同行程內斷言，而且雙向——同 seed 相等、異 seed 不同。
執行緒例外＝測試失敗 pyproject.toml：filterwarnings = ["error::pytest.PytestUnhandledThreadExceptionWarning"]。 註解說明理由：「執行緒裡的未處理例外不准只是 warning——那正是『寫者死掉、最終值不對』的間歇失敗來源。」

假件一律叫 Fake*（不叫 Mock*），住在 emforge/testing.py， 使用者寫自己的策略測試也能 import。FakeSimulator 是確定性的假儀器： 同 bits 同響應、不同 bits 不同響應，可以指定哪些 id 失敗、哪些卡住（模仿 COM 偶發例外與看門狗）。

15.3　四種測試策略

（a）契約測試——一套規格、多個實作

見 6.5。這是「基礎設施解耦」宣稱的唯一硬證據：同一組 36 條斷言對 FileDepot 與 MemoryDepot 各跑一次。沒有這個，「換後端零改 runtime」就只是一句話。

（b）adapter parity——500 筆逐位元

tests/adapters/test_antenna_bound.py::test_measure_parity_500_random_responses_bitwise： 產生 500 筆隨機響應，用 vendored 的 numpy 尺與舊 antenna.losses 各算一次， 斷言 m1…m6 逐位元相等。同一個檔還有兩條：凍結的 targets 與舊 yaml 設定值相等、 adapter 宣告的 geom_ver 與舊模組的 GEOM_VER 常數相等。

這三條是「vendor 一份尺」這個決定的安全網——沒有它們，兩份程式碼會慢慢漂開而沒人知道。

（c）靜態守門——規範的機器版

見 4.3。11 條，全部用 AST 掃描，不執行受測程式，所以又快又不受環境影響。

（d）端到端

tests/test_e2e.py 五條，每一條驗一個跨模組的性質：

  • 雙策略全鏈路：兩個策略 ＋ 假 worker → 資料庫 → 公證 → 待審 → promote → 報表。
  • 中途重啟續收不重複：批跑到一半殺掉 runtime，重起之後接著收，不會產生重複紀錄（I-12）。
  • 核心全程不 import torch：跑完整條鏈路之後檢查 sys.modules。
  • 雙實例讀可寫不可：第二個 profile 的實例讀得到第一個的資料，但寫不進去（D2）。

  <store>/<sha>.pt                     SampleStore 的 (x, y) tuple，**內容 hash 命名**——無法從 id 反推
  <store>/hfss_setup.json              這批的求解設定
  <store>/rad/<legacy_id>.pt           方向圖（single）
  jobs_state/<store>.done              誰跑的
  harvest_*/                           只有 tuple 檔，沒有 manifest

四條規則

規則內容
profile 自動映射 看 hfss_setup.json：把「值等於預設」的求解鍵先扣掉（舊 store 常把預設明寫出來）， 剩下的若還有幾何／網格變體（slot_spec、pixel_count ≠ 25…）就不映射—— 沿用舊規則「永不入鍋」。dual 另外檢查 store 內 geom 是否一致。 映射不到的印 ✗ unmapped: 原因，可用 --map store=profile 強制。
pattern-bytes join 舊 tuple 檔用內容 hash 命名，沒辦法從 legacy id 找到它。做法是把 <store>/*.pt 全部載入、以 packbits(x).tobytes() 建索引，再用 <store>_input/<id>.pt 的 pattern 去查。 同一個 pattern 有多筆量測時，用舊 results.json 的 wm 欄（2 位小數）比對挑對的那一筆。
量測重算，不抄舊值 所有 measure／score 都用新的凍結尺重算。 --verify 把重算結果與舊 wm 欄比對（容差 0.006 ＝ 2 位小數）， 零 verify_fail 才算「新尺 ＝ 舊尺」的實證；有不符 → exit 2。
可重跑 db/<profile>/_imported.json 記每個 store 的簽名（results.json 的 mtime ＋ .pt 檔數）； 未變的 store 直接 skip。--force 忽略簽名，--dry-run 只印計畫。

匯入的紀錄 strategy 欄填 legacy:<store>、worker_ver 填 "legacy"， 原始的 manifest 與 results entry 整份放進 note.legacy——所以任何一筆都能追回舊系統的來源。 error 列預設跳過（--include-errors 才收）；方向圖進 Record.extra["radiation"]（--no-rad 可略）。
